Markdownは「どこでも同じように表示される単一の言語」ではありません。軽量マークアップとしての共通部分がある一方で、レンダラーごとに拡張や制限があります。**まず標準的な構造を守り、公開先で必要な拡張だけを追加する**ことが、移植性と保守性を両立する基本方針です。

このサイトでは、日常的なソフトウェア開発で接点の多い **GitHub Flavored
Markdown（GFM）**
を中心に解説します。GFMはCommonMarkを基にしており、表、打消し線、タスクリスト、自動リンクなどの拡張を定義しています。[1]

## 使い分けの考え方

| 公開先                     | まず使う記法                         | 追加で確認すること                            |
| -------------------------- | ------------------------------------ | --------------------------------------------- |
| GitHubのREADME、Issue、PR  | GFM                                  | アラート、Issue参照、タスクリスト、HTMLの制限 |
| GitHub Wiki                | GFMを基本にページ間リンク            | ルート相対パスとページ名の扱い                |
| Astro Starlight            | CommonMark系Markdownとコンポーネント | フロントマター、サイト固有コンポーネント      |
| VS Codeのプレビュー        | 組み込みMarkdown機能                 | Mermaid、KaTeX、ローカルリンク検証            |
| 複数の公開先に流用する本文 | CommonMark寄りの基本記法             | 拡張記法を注記または代替表現へ分離            |

## このガイドの読み方

最初に[クイックリファレンス](./quick-reference/)で、毎日使う記法を把握してください。次に[基本構文と構造](./syntax/)で読みやすい文書の骨格を確認し、GitHubで作業する場合は[GitHubで使うGFM](./github/)へ進みます。図、数式、画像を扱う場合は[図表・数式・メディア](./rich-content/)を参照してください。

執筆環境やチーム運用を整える際は、[VS Code執筆環境](./authoring/)、[品質管理と自動化](./quality/)、[公開と移行](./publishing/)を順に読むと、個人のメモから継続運用する公開ドキュメントまでを一貫して整備できます。

## 実務で守る五原則

1. **見出しから始める。**
   文書の目的を表す`#`見出しを一つ置き、見出しレベルを飛ばさずに構成します。
2. **表示先を決める。**
   GFM、Starlight、社内Wikiなど、最終的なレンダラーを決めてから拡張記法を選びます。
3. **リンクを資産として保守する。**
   相対リンクを優先し、見出しやファイル名を変えるときは参照元も確認します。
4. **コードと画像を説明する。**
   コードフェンスには言語を指定し、画像には内容を説明する代替テキストを付けます。
5. **公開前に機械検査する。**
   Linter、整形、ビルド、リンク確認をレビューの前後に実行します。

> AIが作成したMarkdownも、通常の変更と同じ品質基準でレビューしてください。もっともらしい見出し、リンク、コード例でも、対象のレンダラーで正しく動くとは限りません。

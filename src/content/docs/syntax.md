Markdownの価値は、装飾の少なさではなく、**ソースを読んでも構造が理解できること**にあります。見出し、段落、リスト、リンク、コードを目的に応じて使い分けると、表示結果だけでなくレビュー、検索、変換、アクセシビリティも改善します。

## 見出しは文書の骨格

H1は文書全体の題名です。通常は1ファイルにつき一つだけ使い、主要な節をH2、その内訳をH3として表現します。見出しは視覚上のサイズを変えるためではなく、内容の階層を示すために使います。

```md
# API運用ガイド

## 認証

### トークンの発行

### トークンの失効

## 障害対応
```

CommonMark系の処理系では、ブロック構造の解釈がインライン要素より先に行われます。空行とインデントを安定して使うと、見出し、リスト、引用、コードブロックの誤解釈を避けられます。[1]

## 段落と改行

通常の改行は、表示上の改行になるとは限りません。一文ごとに強制改行を入れる必要はありません。段落を変えるときは空行を一つ置きます。

```md
これは一つ目の段落です。同じ段落として続きます。

これは二つ目の段落です。
```

行末の二つ以上の半角空白はハード改行として解釈されますが、エディターが空白を除去しやすく、レビューでも見落とされがちです。意図的な改行が必要なときは、公開先の規約に従って`<br>`または文章構造の見直しを検討してください。

## 引用と要約を分ける

引用は第三者の文章や仕様の抜粋に使います。自分の結論、要約、注意事項を引用記号で囲まないようにします。

```md
> Markdownの設計目標は、ソースのままでも読みやすいことです。
>
> — 出典へのリンク
```

引用の前後には、自分の文脈を添えます。長い引用は避け、一次資料へリンクし、必要な部分だけを抜き出します。

## リストは粒度をそろえる

一つのリスト内では、文の形式をそろえます。たとえば、すべてを動詞から始める、すべてを名詞句にする、と決めます。親項目の説明と子項目の作業を混在させないことも重要です。

```md
- リリース前に確認する項目
  - 変更履歴を更新する
  - 自動テストを実行する
  - 公開URLを確認する
```

ネストを深くしすぎると、狭い画面とプレーンテキストの両方で読みにくくなります。三階層を超えるなら、節を分けるか表へ再構成してください。

## リンクは文脈を持たせる

`こちら`やURLそのものをリンクテキストにするより、遷移先と行動がわかるテキストを使います。

| 避ける例                      | 推奨例                                      |
| ----------------------------- | ------------------------------------------- |
| [こちら](https://example.com) | [障害対応手順](https://example.com)         |
| <https://example.com>         | [公開環境の状態ページ](https://example.com) |

同じリポジトリ内では相対リンクを使うと、フォーク、プレビュー、ブランチで追跡しやすくなります。ファイルや見出しを変更するときは、VS
Codeの参照検索やリンク検証を使って参照元を確認してください。

## コードは実行可能な最小例にする

コードブロックは説明の補助ではなく、再現可能な証拠として扱います。言語指定を付け、前提条件、期待する出力、破壊的な操作の有無を添えます。

```bash
npm run lint
npm run build
```

長いログや認証情報、実行環境固有の絶対パスをそのまま載せないでください。秘密情報は削除し、値の形式が必要なら`YOUR_TOKEN`のようなプレースホルダーで表現します。

Markdownはプレーンテキストなので簡単に変更できます。しかし、簡単に変更できるからこそ、見出し階層の崩れ、リンク切れ、表の破綻、画像の説明漏れ、古い手順の放置が起こります。**人による内容レビュー**と**機械による一貫性検査**を分けて運用してください。

## markdownlintで構造を検査する

markdownlintはMarkdown/CommonMark向けの静的解析ツールです。見出しの段階的な増加、空行、コードフェンスの言語、画像の代替テキスト、リンク断片、表の形式などをルールとして検査できます。[1]

このリポジトリでは次を実行します。

```bash
npm run lint
```

`.markdownlint.jsonc`では、行長の制限を無効化しつつ、同じ階層にある見出しの重複だけを問題にする設定にしています。これは日本語の文章、URL、コード例を無理に改行しすぎないためです。ルールを無効化する場合は、好みではなく公開先の要件とレビュー負荷を根拠に決めます。

## Prettierで差分を小さくする

整形が人によって異なると、内容とは関係ない差分が増えます。PrettierはMarkdown、YAML、JSON、JavaScriptなどを整形できるため、設定ファイルと本文のスタイルをそろえるのに役立ちます。

```bash
npm run format:check
npm run format
```

自動整形は文章の意味を理解しません。整形後には、箇条書きの意図、コードブロック、表、参照リンクが読みやすい状態かを確認してください。

## ビルドを公開前検査にする

Starlightで公開するMarkdownは、次のコマンドで型・コンテンツ検査と静的サイト生成を行えます。

```bash
npm run check
npm run build
```

ビルドに成功しても、外部リンク先の有効性、事実の正確性、手順の安全性までは保証されません。ビルドは「サイトとして生成できる」ことを確認する工程であり、内容の妥当性は別のレビュー項目です。

## Pull Requestでの最小チェックリスト

| 段階       | 自動確認          | 人が確認すること                         |
| ---------- | ----------------- | ---------------------------------------- |
| 作成時     | Linterと整形      | 目的、対象読者、変更範囲                 |
| レビュー時 | ビルド            | 手順の正確さ、用語、リンク文言、画像説明 |
| マージ前   | CIの成功          | 破壊的変更、公開先の表示、移行案内       |
| 公開後     | Pagesデプロイ状態 | 実際のURL、モバイル表示、既存リンク      |

レビューコメントは「この書き方は好みではない」ではなく、「どの読者が、どの場面で、何を誤解するか」を示すと、ルール化や改善につながります。

## AI生成コンテンツの品質基準

AI生成の文章、コード、図の説明は、次の理由で検査対象です。

- 実在しないURL、API、コマンドを示すことがある。
- 現行仕様と異なる古い情報を混ぜることがある。
- もっともらしいが曖昧な手順で、失敗時の復旧がないことがある。
- 入力に含まれた秘密情報や個人情報を出力へ再掲することがある。

AIは構成案、下書き、言い換え、要約の補助に使えますが、出典確認、コード実行、対象環境での表示確認、最終責任は人が担います。
